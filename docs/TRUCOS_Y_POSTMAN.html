Qué es este documento

Guía de uso del sistema con todas las peticiones de Postman listas para copiar. Cada request incluye método, ruta, body y para qué sirve. Solo tienes que cambiar los {{ids}} por los de tu base; el resto funciona tal cual.

Regla de oro: ejecuta primero el Login. El token queda en la variable de colección accessToken y todas las demás peticiones lo heredan.

Lo que necesitas

  • Stack arriba: docker compose -f docker/compose.local.yml up -d
  • Datos demo: python database/bootstrap_demo.py
  • Postman con la colección y el environment Vivent Local

Atajos

  • Swagger: http://localhost:8080/swagger-ui/index.html
  • App: http://localhost:3000
  • Base de datos: http://localhost:8090 (Adminer)

Los ids se obtienen con una llamada y quedan guardados automáticamente en las colecciones. Si trabajas a mano, aquí está el origen de cada uno.

20 trucos que valen puntos

  1. Login una sola vez. El token vive en la variable de colección; el environment no lo declara a propósito.
  2. El refresh rota. Cada /auth/refresh invalida el token anterior: reusarlo devuelve 401. Es la prueba de la rotación.
  3. Logout revoca de verdad. Después de /auth/logout, el refresh usado ya no sirve.
  4. Diferencias de fecha. sales-summary, products, transfers-summary y adjustments-summary reciben ISO (2026-10-01T00:00:00Z); purchases-summary y cash-closures-summary reciben fecha simple (2026-10-01).
  5. Kardex: sourceId es el id del detalle (sourceType = SALE_DETAIL), no el de la venta.
  6. Cierre único: un cierre por usuario + sucursal + día. La colección calcula una fecha libre en un pre-request.
  7. Estados del cierre: crear (CLOSED) → aprobar (APPROVED) → reabrir (REOPENED) → cerrar con monto (CLOSED).
  8. Descuento a nivel venta: exige sales.apply_discount; con seller da 403.
  9. Quitar línea: sales.remove_item; sin él se pide autorización de supervisor.
  10. Traslado en 3 usuarios: transfers_destination solicita y recibe, admin aprueba, transfers_origin despacha. Así se ve la separación de funciones.
  11. Anular venta: pide motivo y cancelDisposition (RETURN_TO_STOCK, LOSS, DAMAGE).
  12. Compra confirmada no se edita: se anula con motivo. Si intentas PUT, responde 400.
  13. Bajas lógicas: para demostrar un DELETE sin romper la cadena, crea un registro temporal y bórralo (así lo hacen las colecciones).
  14. Ajuste no toca stock hasta aprobarse. Ideal para explicar la máquina de estados.
  15. Open Food Facts: código 3017620422003 = Nutella; 0000000000000 = found:false. Solo el rol con products.create ve el diálogo de registro en el POS.
  16. Photon: ?q=Cuilapa devuelve lat/lng y etiqueta; q= vacío devuelve found:false (200, no 500).
  17. Swagger sin token en /swagger-ui/index.html para que el catedrático revise la API.
  18. Permisos en backend: GET /api/v1/users con token de seller da 403. No es que el botón esté oculto: la API lo rechaza.
  19. Reportes con filtros: exporta CSV e imprime desde el botón; el CSV respeta el filtro activo.
  20. Repetible: la colección completa y la de POS generan un runId en el login, así puedes correrlas varias veces sin chocar con SKU ni números de documento.

Colección completa (128 requests)

Las 14 carpetas de Vivent.postman_collection.json. Todas heredan Bearer {accessToken} del login.

00 · Público

Endpoints sin token. Se usan antes del login para cargar la empresa por subdominio.

GET/api/v1/public/tenant-config?subdomain={{tenantSlug}}
Tenant config (público)

Nombre comercial, colores, moneda y módulos habilitados. Es lo primero que hace el frontend.

Sin body (usa el token del login).

01 · Autenticación

Login, sesión, refresh y logout. El login guarda `accessToken`, `refreshToken`, `companyId`, `branchId` y `userId`.

POST/api/v1/auth/login
Login (guarda tokens)

Autentica por tenant + usuario. En Tests guarda el par de tokens y los ids del contexto.

{
  "tenantSlug": "{{tenantSlug}}",
  "username": "{{username}}",
  "password": "{{password}}"
}
GET/api/v1/auth/me
Sesión actual (/auth/me)

Usuario dueño del token.

Sin body (usa el token del login).

POST/api/v1/auth/refresh
Refresh token (renueva y rota)

Canjea el refresh por un par nuevo; el anterior queda revocado.

{
  "refreshToken": "{{refreshToken}}"
}
POST/api/v1/auth/logout
Logout (revoca refresh)

Revoca el refresh token presentado.

{
  "refreshToken": "{{refreshToken}}"
}
POST/api/v1/auth/login
Login con clave incorrecta (401)

Caso de error: 401 INVALID_CREDENTIALS.

{
  "tenantSlug": "{{tenantSlug}}",
  "username": "{{username}}",
  "password": "clave-incorrecta"
}
